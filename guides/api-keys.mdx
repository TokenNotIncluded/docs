Tokenz uses secret API keys to authenticate every request you make to the API. Include your key as a Bearer token in the `Authorization` header — no sessions, no cookies, no OAuth flows. Every call you make to the Tokenz API must carry this header or the request will be rejected with a `401 Unauthorized` error.

## Authenticating a request

Pass your secret key in the `Authorization` header on every API call:

```bash authenticate.sh
curl https://api.tokenz.one/v2/checkoutsession \
  --header 'Authorization: Bearer secret_test_YOUR_KEY_HERE'
```

## Test vs. live keys

Every Tokenz account has two sets of keys: one for testing and one for live production traffic. The key prefix tells you which environment it belongs to.

| Prefix | Mode | Moves real money? |
|---|---|---|
| `secret_test_…` | Test | No — simulated only |
| `secret_live_…` | Live | Yes — real payments |

Test keys cannot create real charges, and live keys cannot interact with test data. Always use a `secret_test_…` key during development and switch to `secret_live_…` only when you are ready to go live.

## Keep your key secret

<Warning>
  **Never include your secret API key in browser code, mobile apps, or any client-side code.** Your key grants full API access under your account. If exposed, an attacker can create sessions, read orders, and issue refunds on your behalf.

  Always read your key from an environment variable (e.g., `process.env.TOKENZ_SECRET_KEY`) and keep it out of source control. Tokenz shows each key **only once** at creation time — store it in a secrets manager or your deployment environment immediately.
</Warning>

## Finding your keys

Navigate to **Dashboard → Developers → API keys** in the [Tokenz Dashboard](https://dashboard.tokenz.one). From there you can view existing keys, create new ones, set scopes, and revoke keys you no longer need.

## API key scopes

Each API key carries a set of permissions called **scopes**. A key can only perform actions covered by its scopes — requests outside those permissions return a `403 Forbidden` error.

Available scopes include:

- **Checkout Session** — `create`, `read`
- **Order** — `read`, `cancel`, `delivery`
- **Product** — `read`
- **Refund** — `create`, `read`
- **Redemption Code** — `validate`, `redeem`
- **Subscription** — plan changes

Follow the principle of least privilege: grant each key only the scopes it needs. For example, a fulfillment service that only reads orders and marks deliveries should not have `refund:create`.

## Rotating keys

You can hold multiple active API keys simultaneously, which means you can rotate a key with zero downtime:

1. Create a new key with the same scopes as the one you are replacing.
2. Deploy the new key to your servers and confirm it is working.
3. Delete the old key from the Dashboard.

Tokenz immediately rejects any request that uses a deleted key, so complete your deployment before removing the old one.

## Webhook signing secrets

Webhook signing secrets are separate from API keys. Each webhook endpoint you register in the Dashboard gets its own signing secret, which Tokenz uses to sign the `Tokenz-Signature` header on every event delivery. You use this secret to verify that the payload came from Tokenz and has not been tampered with.

The signature is computed as an HMAC-SHA256 digest of the timestamp and raw request body, encoded in base64. See the [Webhook Integration guide](/guides/webhook-integration) for full verification instructions and example code.

## Authentication errors

| HTTP Status | Meaning |
|---|---|
| `401 Unauthorized` | The `Authorization` header is missing, malformed, or the key does not exist |
| `403 Forbidden` | The key is valid but does not have the scope required for this operation |
