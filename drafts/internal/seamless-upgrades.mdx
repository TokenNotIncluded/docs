软件包只在 `/usr/bin/lmm-api` 暴露一个公开的后端与运维 CLI。服务运行、健康检查、HTTP 请求和部署都是该 CLI 的子命令;不支持源码树里的部署辅助脚本,也不支持第二个公开部署命令。T0 过渡期可以存在由软件包拥有的临时兼容链接 `/usr/bin/lmm-api-go`,但文档、服务、自动化脚本和新版本发布都必须使用 `/usr/bin/lmm-api`。

应用级服务器控制请使用原生 CLI:

```bash
ssh ArchDmit /usr/bin/lmm-api status
ssh ArchDmit /usr/bin/lmm-api doctor
ssh ArchDmit /usr/bin/lmm-api request --show-status /api/status
```

这里的 SSH 只是传输通道。主机层面的检查(systemd、文件系统、内存和 journal 读取)仍单独进行,并且在没有显式授权受保护的部署事务时保持只读。

## 当前生产边界

2026-08-14 的只读审计显示,`api.lmm.best` 运行 Go 后端,使用 PostgreSQL 和专用 Valkey。规范化的小写 `pg-write-boundary` 与 `cutover-journal` 在事务、模式和修订版本上一致,journal 阶段为 `COMPLETE`,`post-cutover-verify.json` 证明 PostgreSQL 历史迁移已通过校验。每次变更前都要重新核对原生生产事务状态以及当前的主机资源与健康测量,不要把这份有日期的观察结果当作长期证据。Rust 仍只用于内部探测,不承载生产业务流量。

## 前端:零停机的静态发布

在 CI 中把前端构建成不可变的签名发布产物,再基于该产物构建精确的 `lmm-api-web-bin` 软件包。生产发布计划把候选与回滚的 Go / Web 软件包、它们的签名发布归档与 Sigstore 捆绑包,以及候选 `lmm-api` 探测二进制配成一对。控制器在写入规范化不可变 JSON 之前,会校验标签、祖先关系、签名、校验和、软件包载荷和路由契约修订版本。

生产使用可续跑的控制器阶段:

```bash
/usr/bin/lmm-api-deploy production plan ...
/usr/bin/lmm-api-deploy production stage \
  --plan <release-plan.json> --plan-sha256 <sha256> --confirm api.lmm.best
/usr/bin/lmm-api-deploy production promote \
  --plan <release-plan.json> --plan-sha256 <sha256> --confirm api.lmm.best
/usr/bin/lmm-api-deploy production status|confirm|rollback \
  --plan <release-plan.json> --plan-sha256 <sha256> --confirm api.lmm.best
```

`stage` 只创建由标记文件拥有的目标工作区并传送经过校验的精确产物。`promote` 执行受保护的软件包事务、健康观察、看门狗和可选的三副本备份协议。远程变更仍然需要当轮授权和精确的主机身份。

前端事务会校验 `index.html` 与本地资源引用,复制到同一文件系统的暂存目录,并原子替换 `/srv/lmm-api-frontend/current`。切换之前先把 `/static` 文件复制进位于 `/srv/lmm-api-frontend/assets` 的累积不可变存储,遇到同名不同内容会拒绝,然后把版本化发布目录置为只读。因此持有上一份 `index.html` 的浏览器在切换后仍能继续懒加载带哈希的分块。`flock` 串行化发布操作,保留策略始终包含当前发布。本阶段不对静态资源做垃圾回收;未来若要做 GC,必须保留每个保留版本引用到的资源。

回滚由同一个受保护事务执行,恢复经过校验的上一版前端发布。不要调用源码树里的发布脚本,也不要构造并行的公开辅助命令。

站点使用自己的 `/etc/nginx/lmm-api-mime.types`,绝不创建或覆盖 nginx 全局的 `/etc/nginx/mime.types`。所有 nginx 输入都通过受控事务发布,不要逐个复制。安装器用 `flock` 串行化,预留唯一的不可覆盖备份,并管理 `/etc/nginx/lmm-api-mime.types`、HTTP `map`、server location 和 `/etc/nginx/conf.d/new-api.conf`。每个候选文件都作为 root 属主 `0644`、同目录临时文件安装,再原子发布。只有在所有文件就位之后,才执行 `nginx -t`、重载 nginx 并确认 unit 仍然活跃。失败时还原每个受管文件原有状态或精确内容,并重新执行校验、重载和服务检查。

server 作用域模板显式包含 `/etc/nginx/lmm-api-mime.types`。模板把已知的后端路由族转发到 3000 端口,保留 WebSocket 与 SSE 行为,以不可变缓存提供共享 `/static` 资源存储,并让入口页面重新校验。缺失的静态或根级公开资源返回 404,而不是返回 SPA HTML。生产环境的 `/terms` 和 `/privacy` 仍精确映射到法律 HTML 文件。

## 后端服务与升级

Systemd 直接运行规范的服务入口:

```ini
ExecStart=/usr/bin/lmm-api serve
```

状态、诊断、HTTP 探测、部署和 GeoIP 维护都是 `lmm-api` 的子命令。生产后端变更属于自主运行、加锁的事务,包含离线备份校验、健康校验、持久审计输出、十分钟回滚看门狗,以及在事务被视为完成前的显式确认。事务不依赖发起它的 shell 或 API 连接,但重启唯一进程会造成有界中断,因此它不是零停机或蓝绿部署。

在未知的历史目标上调用子命令之前,先在不执行未经验证的旧二进制的前提下判定已安装软件包和 systemd `ExecStart`。受支持的服务契约是 `ExecStart=/usr/bin/lmm-api serve`,规范路径必须由已批准的 Go 软件包拥有且没有任何被改动的文件。旧版判定应使用软件包与 systemd 元数据、运行中的 PID、经过清洗的进程环境方案检查以及显式 HTTP 探测,然后先完成受保护的 T0 事务,再依赖统一控制器。

始终以 `apps/api-rust/tests/fixtures/routes/route-gate.tsv` 为准了解当前的路由归属与审批状态;说明性文字不能作为路由数量的权威依据。

## Rust 内部探测的蓝绿基础

原生 Rust 蓝绿部署基础使用 `127.0.0.1:3100` 作为 blue、`127.0.0.1:3101` 作为 green。Nginx 只拥有受回环限制的 GET/HEAD 存活、就绪和构建探测。发布、按槽位符号链接、nginx upstream 发布、PREPARED/COMMITTED journal、崩溃对齐和有界 SIGTERM 排空都与 Go 进程无关。无论是挂载的候选版本还是历史内部探测演练,都不拥有生产流量;参见 `docs/rust-blue-green.md` 与迁移 TSV。

该基础不是生产 API 切换。在所有路由通过独立差分门禁且 PostgreSQL 切换获批之前,生产业务路由仍留在已批准的后端上。

## PostgreSQL 生产迁移与对齐前置条件

经过校验的 SQLite 到 PostgreSQL 复制器和自主协调器,仍是新迁移或对齐的唯一认可路径。线上目标可能已在某次历史切换后以 Go + PostgreSQL + 专用 Valkey 运行,但这一运行事实并不能证明当前边界、模式契约或带认证的灰度探针已被接受。当活跃进程使用 PostgreSQL,而当前 `PG_WRITE_BOUNDARY` 或 journal 缺失、或切换后校验失败时,应停止并先做对齐,再改变后端归属。协调器会在仍涉及 SQLite 源时停止 Go 写入方,备份并校验源,复制到全新的版本化模式,在发布 PostgreSQL 与 Valkey 配置之前持久标记仅向前的边界,并运行公网与带认证的灰度探针。严格的 journal、不可变候选哈希、`--reconcile-only` 路径和 systemd 启动门禁使进程死亡与重启都能幂等恢复。

一次性数据库切换不是零停机:SQLite 冻结会停止唯一的 Go 进程,并断开活跃的 HTTP、SSE 和 WebSocket 连接。在隔离演练通过并且运维人员显式批准维护窗口之前,生产环境继续禁止该操作。

在业务流量切换到 Rust 之前,路由、认证、配额、计费和流式对等性,与 N 和 N-1 兼容的扩展与收缩迁移,单例后台任务归属,带认证的灰度探针,以及 SSE / WebSocket 的优雅排空与重连,仍然是必须完成的条件。Nginx 不得自动重试非幂等请求。

推荐的发布顺序是:先做仅前端发布(仅当其 API 请求仍与 Go 兼容时)、观察并人工确认、再做 Rust 内部探测、Rust 业务灰度,最后执行受保护的后端切换。挂载了 Rust 槽位、`/readyz` 返回成功或做过旧的蓝绿演练,都不能替代路由门禁与成对监听证据。
