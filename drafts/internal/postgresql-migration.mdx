本文描述针对 PostgreSQL 18 目标的可审计离线演练与校验流程,不授权也不实现生产切换。生产环境可能在某次历史协调器运行后已经以 Go + PostgreSQL 运行,但这一运行事实不能替代当前的边界、模式、灰度探针、备份与运维证据。

新的契约 1 PostgreSQL 基线要求 `users.console_activated_at BIGINT NOT NULL DEFAULT 0`。这份全新模式契约不会升级已有的 PostgreSQL 模式。契约 2 是单独评审、仅向前的扩展步骤,针对挂载到 Rust 路由的八张开源赏金表,它不会改变已冻结的 34 张表清单。

## 证据与范围

版本化清单定义了 34 张应用表及其列、键、索引、转换器、序列归属和校验规则。CI 在 PostgreSQL 18 上演练该契约,并校验 34 张表、424 个列、172 个索引和 29 个自有序列。

## 命令

在 `apps/api-rust/` 下运行:

```bash
cargo run -p lmm-db-migrate -- manifest-validate \
  --manifest crates/lmm-db-migrate/schema/table-map.json

cargo run -p lmm-db-migrate -- inspect \
  --sqlite /path/to/offline/one-api.db \
  --manifest crates/lmm-db-migrate/schema/table-map.json \
  --report /path/to/audit/inspect.json

export LMM_MIGRATE_DATABASE_URL='postgresql://migration-role@/database?host=/run/postgresql'

cargo run -p lmm-db-migrate -- rehearse \
  --sqlite /path/to/offline/one-api.db \
  --manifest crates/lmm-db-migrate/schema/table-map.json \
  --baseline crates/lmm-db-migrate/schema/postgresql-baseline.sql \
  --catalog-sql crates/lmm-db-migrate/schema/export-postgres-catalog.sql \
  --schema lmm_rehearsal_20260801 \
  --report /path/to/audit/rehearse.json

cargo run -p lmm-db-migrate -- verify \
  --sqlite /path/to/offline/one-api.db \
  --manifest crates/lmm-db-migrate/schema/table-map.json \
  --schema lmm_rehearsal_20260801 \
  --report /path/to/audit/verify.json

export LMM_MIGRATE_DATABASE_URL='postgresql://migration-role@/database?host=/run/postgresql'
cargo run -p lmm-db-migrate -- forward \
  --schema lmm_rehearsal_20260801 \
  --contract-migration migrations/0002_open_source_bounty_schema.sql \
  --report /path/to/audit/forward.json \
  --contract-id 2 \
  --contract-sha256 "$(sha256sum migrations/0002_open_source_bounty_schema.sql | awk '{print $1}')" \
  --min-reader-version 1 --max-reader-version 2 \
  --min-writer-version 1 --max-writer-version 2 \
  --release-id release-contract-2 \
  --release-sha256 SHA256_RELEASE_ARTIFACT \
  --component-sha256 api-server-binary=SHA256 \
  --component-sha256 api-server-revision=SHA256 \
  --component-sha256 db-migrator-binary=SHA256 \
  --component-sha256 postgresql-baseline=SHA256 \
  --component-sha256 table-manifest=SHA256 \
  --component-sha256 postgres-catalog-exporter=SHA256 \
  --component-sha256 platform-contract-sql=SHA256 \
  --component-sha256 migration-provenance=SHA256 \
  --component-sha256 legacy-route-oracle=SHA256

bash crates/lmm-db-migrate/scripts/rehearse-postgres.sh
crates/lmm-db-migrate/scripts/verify-provenance.sh
```

PostgreSQL DSN 只通过 `LMM_MIGRATE_DATABASE_URL` 传入,绝不接受命令行参数,也不会写入审计报告。

## 离线源边界

所有涉及源库的命令都拒绝符号链接、特殊文件,以及 SQLite 的 `-wal`、`-journal`、`-shm` 附属文件。打开源库之前,`rehearse` 和 `verify` 会记录其规范路径、设备号、inode、大小、纳秒级修改时间和 SHA-256。已打开的文件描述符会立即再次测量与哈希,并在通过其 `/proc/self/fd` 路径以只读方式打开 SQLite 期间持续保留。这样既关闭了路径替换窗口,又保留了 SQLite 的读锁语义。

整个 COPY 与源侧校验期间保持同一个 SQLite 只读事务。PostgreSQL 提交之前,会再次检查路径身份、元数据、SHA-256、模式契约以及是否存在附属文件。只有在 PostgreSQL 成功提交之后才提交 SQLite 事务,因此受保护的源快照不会被提前释放。

## 演练事务

目标模式标识必须符合严格的小写标识符契约。事务作用域的 PostgreSQL advisory lock 串行化该模式的创建,并在同一事务内检查模式是否存在。

基线被应用到新的隔离模式。34 张表全部使用清单中显式列出的列和转换器通过 PostgreSQL COPY 流式写入。行序按完整主键排序:SQLite 文本键按字节序,PostgreSQL 文本键使用 `COLLATE "C"`。JSON、布尔值、UTC 时间戳、定点小数、有限 REAL 值、NULL 以及 COPY 控制字符都有明确的规范化行为。

COPY 之后,29 个自有序列通过 `setval` 推进;空表的正确处理结果是 `nextval = 1`。运行时 PostgreSQL 目录会按清单校验,随后分别读取 SQLite 与 PostgreSQL,用逐表计数和规范化 BLAKE3 表哈希比对。财务聚合校验覆盖用户、令牌、日志、配额数据、充值、订阅订单和渠道,但不会输出聚合值。

账户余额对等性是一个增量的向前步骤,不改写已发布的表清单。在已有 PostgreSQL 模式上,按常规向前迁移评审流程以模式契约 10 应用 `migrations/0010_account_balance_access.sql`。向前校验器检查 `tokens.account_balance_read BOOLEAN NOT NULL DEFAULT FALSE` 的精确形态;重复运行该迁移是幂等的,已有键继续保持拒绝状态。

COPY、目录、序列或校验失败都会回滚整个目标模式事务。`verify` 使用只读、可重复读的 PostgreSQL 快照。

## 审计输出

成功与失败报告都以 `0600` 权限创建,通过同目录临时文件写入、fsync、原子重命名,随后对父目录执行 fsync。报告不包含 DSN、行值、主键值、财务数值或底层错误文本。失败报告只包含稳定的阶段与错误类别。标准错误输出使用相同的分类,不打印转换值或 PostgreSQL / SQLite 错误细节。

## 生产事务

已废弃的 shell 协调器不是生产入口。供应方原生的迁移与部署操作只能通过 `/usr/bin/lmm-api` 调用,并遵循 [PostgreSQL 切换](/docs/postgresql-cutover)与规范性的[后端 CLI 部署契约](/docs/backend-cli-deployment-contract)。

迁移命令可以创建或校验隔离模式,也可以应用显式绑定契约的向前迁移,但不能静默授权流量或供应方归属。如果线上目标是 PostgreSQL,先校验活跃模式、持久写入边界、候选与软件包哈希以及带认证的灰度探针。证据缺失或校验失败会阻止迁移和后端选择。

一旦可能越过了 PostgreSQL 写入边界,应用回滚就是人工操作,且只恢复与当前模式兼容的 N-1 代码、供应方链接、前端和配置,绝不恢复 SQLite 或数据库快照。PostgreSQL 始终是持久权威;Valkey 承载可重建的缓存、会话与吊销以及限流状态。
