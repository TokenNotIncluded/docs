Go 后端在转换、重试和流式转发上游请求期间会保留请求数据。请求体大小限制不等于进程内存上限:解析后的 JSON、供应方 DTO、编码缓冲区和并发请求都会叠加占用。

## 请求路径的行为

- 大请求体可以溢出到配置的磁盘缓存。默认目录是 Go 临时目录(Unix 下的 `TMPDIR`)中的 `new-api-body-cache`。如果 `/tmp` 是 tmpfs,它仍然是内存支持的存储,而不是普通磁盘。
- gzip、Brotli 和 Zstandard 解压后的长度未知,因此不能根据原始压缩后的 `Content-Length` 选择较小的内存缓冲区,也不能据此绕过大型请求准入。压缩字节与解压字节两个上限都继续生效。Zstandard 使用惰性单流解码,不做预取的异步解码。即使提前拒绝,解码器资源也会被关闭;HTTP 服务器保留对原始网络请求体的所有权,因此拒绝请求不需要等待未读取的慢速发送方完成上传。
- `json.RawMessage` 和 `[]byte` 字段的深拷贝改为批量克隆,不再逐字节反射分配。转换后的请求同样适用,且不会与原始 DTO 共享可变字节数组。
- Responses 与 Chat Completions 的透传路径只隔离顶层请求元数据,不深拷贝将被原样重放的载荷。经过转换的路径保留深拷贝,以免供应方的修改破坏重试。
- 关闭内存存储会释放其持有的缓冲区引用。已经打开的 replay 读取器保持独立且可继续使用;关闭后再打开新读取器会失败。当所有权移交给存储或执行清理时,旧的字节缓存会被清空。这只是让数据可被回收,不会强制 Go GC 或操作系统立即回收。

JSON 解析和编码仍会分配完整值。请求体溢出并不代表 JSON 处理是常量内存的,透传优化也不适用于必须转换或覆盖 JSON 载荷的路由。

## 可选的大型请求准入

这些设置在创建 Go 路由时读取一次,修改后需要重启。它们按**进程**生效,由所有已认证的 HTTP 中继协议和 playground HTTP 请求共享,不是在多个副本之间分配的配额。

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `RELAY_LARGE_REQUEST_MAX_CONCURRENCY` | `0` | 同时在途的大型 HTTP 请求上限;`0` 表示关闭该控制。 |
| `RELAY_LARGE_REQUEST_THRESHOLD_MB` | `4` | 请求体达到或超过该 MiB 值时占用一个名额。 |

长度未知的请求体(包括解压后的请求体)会保守地占用名额。已知的小请求体、空请求体、GET、HEAD 和 OPTIONS 不经过该池。WebSocket 升级与帧以及后台任务执行不在覆盖范围内;任务提交的 HTTP 处理器只在其 HTTP 处理生命周期内被覆盖。

准入发生在认证之后、请求体与模型解析之前。名额持续到处理器返回,流式响应期间同样占用。名额在正常返回、客户端取消且处理器退出后,或发生 panic 时释放,不存在排队等待。饱和时返回 **HTTP 429**、`Retry-After: 1`,以及固定错误码 `large_request_concurrency_exceeded`(Google 原生客户端会收到 ErrorInfo)。OpenAI、Claude 和原生 Gemini 路由保留各自的错误封装。

客户端应遵守 Retry-After 并采用有界退避与抖动,而不是紧凑重试。长时间流和慢速上传可能长时间占用名额;该共享池不是按用户公平的调度策略。请保持合适的客户端、代理与上游超时。既有的 413 字节上限、模型限流、配额检查和系统性能 503 保护仍然是独立控制。

默认关闭,以避免升级后静默改变现有实例的准入行为。并发值非法或为负时回退为关闭并记录启动告警;阈值非法、非正数或溢出时回退为 4 MiB。

小规格实例的一个初始启用配置是:

```dotenv
RELAY_LARGE_REQUEST_MAX_CONCURRENCY=2
RELAY_LARGE_REQUEST_THRESHOLD_MB=4
```

它可以避免多条大型请求处理流水线同时进入,但不是对总堆内存或 RSS 的字节级上限,也不保证任意两个请求都能容纳。单个特别大的请求仍可能超出可用预算。请保留单请求限制与 cgroup 限制,再根据真实流量调优。

## 小内存 systemd 部署

对于设置了 `PrivateTmp=yes` 的服务,要检查**服务挂载命名空间内**的文件系统,而不只是宿主机的 `/tmp`。如果 `/var/tmp` 是可写、磁盘支持的私有挂载,可以通过 drop-in 设置:

```ini
[Service]
Environment="TMPDIR=/var/tmp"
Environment="GOMEMLIMIT=192MiB"
```

确认后续没有 EnvironmentFile 覆盖这些设置。示例中的 Go 预算是约 1 GiB 主机的起点,不是通用默认值。调低它会增加 GC 与 CPU 开销以及延迟。要为其他服务、非 Go 分配和页缓存保留内存;256 MiB 的 Go 预算并不意味着 256 MiB 的 RSS。磁盘支持的文件缓存仍会计入 cgroup 内存用量,尽管它比 tmpfs 数据更容易回收。不要关闭已有的内存保护,也不要为了掩盖过载而盲目提高其阈值。

重启后在代表性流量下核对:

- `/proc/<pid>/environ` 中生效的 `TMPDIR` 与 `GOMEMLIMIT`;
- 实际缓存文件路径与文件系统(不要读取请求内容);
- cgroup 的 `memory.current`、`memory.peak`、`memory.events`、swap 和 memory PSI;
- 宿主机 `MemAvailable`、CPU / GC 开销、请求延迟和真实中继响应;
- 把 429 准入拒绝与本地内存 503、上游 503 分开统计。

仅状态端点返回 200 不能验证上游中继流量。不要删除活跃的请求体缓存文件、清空 Valkey 数据,或用周期性强制重启替代内存预算。回滚部署调优时只移除自己的 drop-in 并重启;把并发改回 `0` 会在下次重启后关闭准入。这些源码变更不会自行部署。

## 测试与分配基准

在 `apps/api-go` 下运行:

```bash
go test ./pkg/admission ./common ./middleware ./relay ./relay/common ./relay/channel ./router
go test -race ./pkg/admission # 在支持竞态检测的平台
GOMAXPROCS=2 go test -run '^$' -bench '^BenchmarkCopyRequestForRelay$' \
  -benchmem -benchtime=3x ./relay
go test -run '^$' -bench '^BenchmarkLargeRequestAdmission$' -benchmem ./pkg/admission
```

拷贝基准对相同 DTO 比较旧的反射拷贝、优化后的深拷贝和透传,其中包含 28 MiB 的 Responses 载荷。报告应给出该操作的分配节省,而不是承诺服务器总内存按比例下降。准入基准包含关闭状态和小请求快速路径。发布前除本地分配基准外,还要使用代表性并发与负载测试以及受支持的 Linux CI。

### 本地分配采样

使用 Go 1.27.1、Android/arm64、`GOMAXPROCS=2`、`GOMEMLIMIT=768MiB`、`-benchtime=3x -count=3` 测量,载荷为合成数据(不是生产请求数据):

| 28 MiB Responses 输入的拷贝方式 | 每次操作分配字节 | 每次操作分配次数 |
| --- | ---: | ---: |
| 旧反射拷贝 | 约 58,722,320 | 29,360,145 |
| 优化后的深拷贝 | 29,362,720 | 16 |
| 透传元数据拷贝 | 768 | 1 |

优化后的深拷贝仍持有独立的 28 MiB 载荷,节省的是被丢弃的逐字节反射分配,并不是取消重试隔离。透传只共享处理器不会修改的数据。转换器查找有少量固定开销:在空载荷 DTO 基准中,相比旧拷贝器多出 640 字节和一次分配。这些是操作级分配结果,**不是**进程总 RSS 或端到端吞吐保证。原生 Linux CI 与负载测试仍是发布门禁。

## 进程内字节缓存分配

`pkg/cachex.ByteCache` 现在随键插入逐步增长 map,不再在构造和 `Purge` 之后按配置的条目上限预留空间,替换已有值时复用其条目与 LRU 节点。这降低了通知与验证缓存以及内存限流器的空闲分配,并在更新请求计数时消除缓存节点抖动。插入、替换和淘汰在原有互斥锁下共用同一实现。

条目上限、权重记账、LRU 顺序、TTL 刷新与重置以及原子 `Compute` 语义都保持不变。超大的 `SetWithTTL` 仍不会改变已有值,超大的 `Compute` 结果仍会被移除,过期仍然是惰性的,`Purge` 只丢弃 map 与条目而不强制 GC。配置的字节预算统计调用方提供的权重,不含 map 与链表开销,也不代表进程总 RSS;填满的 map 在 purge 之前可能保留容量。

Linux/amd64 合成分配测量,Go 1.25.1,每种场景三次运行:

| 操作 | 之前(字节/次) | 之后(字节/次) |
| --- | ---: | ---: |
| 创建空缓存,256 条目上限 | 13,784 | 176 |
| 创建空缓存,16,384 条目上限 | 约 873,912 | 176 |
| 创建空缓存,65,536 条目上限 | 约 3,495,223 | 176 |
| 替换已有整数,`SetWithTTL` | 112(2 次分配) | 0(0 次分配) |
| 递增已有整数,`Compute` | 112(2 次分配) | 0(0 次分配) |
| 插入一个整数后 purge,65,536 条目上限 | 约 3,495,206 | 368 |
| 插入并淘汰不同字符串键,256 条目上限 | 119 | 119 |

这些数字衡量的是指定操作的分配量,不是保留堆或整机节省。新键仍会分配节点,按需增长索引只是把 map 增长的开销转移到插入时。用户回调与值也可能分配;这里的零分配更新使用整数值和简单回调。这些微基准不构成任何生产吞吐或延迟结论。

在 `apps/api-go` 下复现:

```bash
go test -race ./pkg/cachex
go test -run '^$' -bench '^BenchmarkByteCache' -benchmem -count=3 ./pkg/cachex
```
