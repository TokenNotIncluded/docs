本文对后端打包和生产部署具有规范性约束。

## 可执行文件布局

后端供应方各自打包为真实的独立可执行文件:

```text
/usr/bin/lmm-api-go
/usr/bin/lmm-api-rs
```

对外的后端入口和运维入口始终是相对符号链接:

```text
/usr/bin/lmm-api -> lmm-api-go
/usr/bin/lmm-api -> lmm-api-rs
```

`/usr/bin/lmm-api` 不得是供应方的普通可执行文件。供应方软件包不得安装 `lmm-api-go -> lmm-api` 这类反向别名。两个供应方软件包可以共存,任何一方都不拥有固定的 `/usr/bin/lmm-api` 载荷。

后端切换操作必须在 `/usr/bin` 中创建临时相对符号链接,校验它的一跳目标是 `lmm-api-go` 或 `lmm-api-rs` 之一,再原子重命名覆盖 `/usr/bin/lmm-api`,并在报告成功前同步 `/usr/bin`。出现符号链接链、绝对目标、目标缺失、供应方二进制可写,或供应方二进制没有经过验证的软件包归属时,一律视为硬失败。

## 调用不变式

生产服务和运维操作必须调用 `/usr/bin/lmm-api`:

```text
/usr/bin/lmm-api serve
/usr/bin/lmm-api migrate --verify
/usr/bin/lmm-api-deploy production status ...
/usr/bin/lmm-api-deploy production confirm ...
/usr/bin/lmm-api-deploy production rollback ...
```

部署代码不得直接执行 `/usr/bin/lmm-api-go` 或 `/usr/bin/lmm-api-rs`。候选版本校验使用发布作用域内的 `lmm-api` 符号链接,其一跳目标是暂存的供应方二进制。软件包检查可以引用供应方文件名,但不能把它们当作运维入口。

## CLI 对等性

`lmm-api-go` 和 `lmm-api-rs` 必须实现相同的公开命令契约、退出码、部署状态格式和安全检查,至少覆盖:

- `serve`、`version`、`status`、`doctor` 和 `request`;
- `migrate --apply|--verify`;
- 前端发布与回滚;
- 生产计划、暂存、晋级、状态、确认和回滚;
- 备份创建、导出、校验和恢复预检;
- 边缘策略安装与校验;
- 打包和 CI 需要的构建与发布校验。

部署等待确认期间允许发生供应方切换,因此任一供应方都必须能够读取、校验、确认或手动回滚由另一方创建的事务。

## 可选的生产备份

发布计划格式 6 要求显式声明 `disabled` 或 `controller-only` 备份模式。仅 Go、仅 Web 以及组合发布可以关闭备份。选择 `controller-only` 时需要对完整的本地备份集合做带认证的校验;目标主机收到的是签名元数据,而不是归档或密钥。两个供应方都必须校验证据格式 3,并为已有事务保留旧格式读取能力。可选的备份不能替代经过验证的 N-1 软件包或配置回滚状态。

## 手动回滚

生产部署没有计划内的自动回滚,不得创建 systemd 回滚服务或定时器,也不得在激活、观察、取消或进程退出处理中调用回滚。

在首次修改线上状态之前,CLI 会在持有事务锁的情况下持久化不可变清单、经过验证的回滚产物和可回滚状态。越过该边界后的失败会进入 `ROLLBACK_REQUIRED`,并保留锁和证据。恢复需要显式的运维命令:

```text
/usr/bin/lmm-api-deploy production rollback ...
```

健康晋级通过观察门禁后停在 `AWAITING_CONFIRMATION`,只有显式的 `confirm` 或 `rollback` 才能让事务终结。失败的回滚仍可重试,并且必须保留恢复证据。

## 仓库布局

根目录的 `deploy/` 不属于目标架构。运行时、发布、校验、迁移和恢复行为应位于两个后端 CLI 或其供应方库中;不可变的服务与配置资产位于打包方目录下。在 `deploy/` 被移除之前,纯 shell 的部署逻辑和 shell 契约测试必须替换为 Go 和 Rust 测试。

如果受跟踪的代码、工作流、软件包或文档重新引入对已移除 `deploy/` 路径的运行时依赖,或把供应方二进制当作生产运维入口调用,CI 必须失败。

## 公开故障信息

边缘节点在无法访问服务时提供一份独立的 LMM Best 说明文档:接受 HTML 的浏览器 GET/HEAD 请求会收到该文档,API 客户端会收到结构化的 503 响应。上游 API 的错误响应体不会被拦截。该文档不依赖应用、JavaScript 包或字体。可读源码位于 `packaging/common/lmm-api/edge-policy/service-unavailable.html`,修改后运行 `node scripts/generate-nginx-error-page.mjs`。

Go 生产运维工具只在前端发布目录旁发布一份很小的公开状态文档,绝不把私有失败信息、凭据、配置或事务清单写入该文档。部署阶段会自动更新说明文案。没有运维人员提供估算时间时不会显示估算;过期估算会标记为已过期;记录的恢复结果需要先通过实时健康端点确认,页面才会宣告服务可用。

运维人员可以发布经过评审的说明和真实的恢复时间:

```sh
/usr/bin/lmm-api-deploy production maintenance \
  --deployment-id "$DEPLOYMENT_ID" --confirm api.lmm.best \
  --state maintenance --service "LMM Best API" \
  --message "Scheduled service update" \
  --expected-recovery-at "$RECOVERY_AT"
```

`RECOVERY_AT` 必须是未来的 RFC3339 时间戳;恢复时间未知时省略该选项。服务名、模型名和说明必须描述真实受影响范围。该命令只修改公告,不会停止、启动服务,也不会绕过访问控制。

内存覆盖校验会在激活和回滚时、停止后端之前执行。严格解析且不超过打包上限 256 MiB 的 Go 堆限制会被保留,包括现有的 192 MiB 缓解值。无法识别的 cgroup 或可执行文件指令仍会在停止服务前以失败告终。

## 历史退款迁移验收

Go 运维工具可以为历史上的 `lmm-api-go-bin 0.2.17-1` 写入方消费位于 `<workspace>/state/legacy-refund-risk.json` 的单实例确认。该确认要求用户显式决策,并且存在一份新鲜且经过校验的控制器备份。这份私有的 root 属主确认文件绑定部署 ID、精确的回滚软件包标识与摘要、写入方 PID 与 systemd 调用,以及 `controller-backup-reference.json` 的摘要和捕获时间。该引用是控制器已验证的数据库、角色与环境备份清单的未修改副本,不是原生格式 3 备份证据,也不声称在目标侧解密。结果未知的仍保持 `unknown`。两类记录都在 24 小时后过期;格式错误、符号链接、属主错误或不匹配的记录一律以失败告终。

该确认只替代针对这个特定写入方的历史“无退款”证明。准入关闭、连接排空、进程正常退出、cgroup 为空、关机日志、签名软件包校验、迁移和健康检查仍然必须执行。记录会随事务保留,供后续对账。这条路径不执行任何额度调整。

新的签名 Go 软件包会声明内容严格为 `v1\n` 的 `REFUND_TASK_DRAIN_CAPABILITY`。只有在软件包归属、发布元数据和正在运行的可执行文件都与事务匹配时才会被接受。这类写入方必须在优雅关停期间输出经过校验的退款执行报告:accepted 等于 finished,active 和 failed 均为零,`execution_complete` 为 true。这只能证明执行完成,不能证明历史资金正确性。这类写入方不要求存在历史意图日志。

## 从旧原生 CLI 暂存

控制器支持签名的 Go 0.2.52 `deploy` 引导流程和当前的私有 `operator` 协议。在创建工作区之前,它会校验已安装的一跳供应方链接、root 属主、安全模式和精确冻结的回滚载荷哈希,再通过只读的帮助调用选择入口。帮助信息未知或有歧义时会在创建工作区前失败。公开入口仍然是 `/usr/bin/lmm-api-deploy`。

创建工作区后出现 SSH 错误,不代表可以换一个命令写法重试。控制器只能从精确的 root 属主原生工作区和 ACTIVE 事务标记中恢复响应。清单、状态、外来事务、不安全路径或不完整标记都需要人工对齐,绝不会被重新标记为 WORKSPACE_CREATED。已有的控制器工作区状态会继续走签名产物暂存和原生校验流程。

这种引导兼容性不能证明数据库回滚兼容。由 #386 跟踪的授权基线变更需要单独进行隔离升级演练,并采用经过批准的手动发布计划。
