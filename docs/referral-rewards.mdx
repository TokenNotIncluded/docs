邀请关系在注册时绑定到一个已启用的既有账户。注册会增加邀请计数,但不再发放邀请方与被邀请方的推荐额度。通用的 `QuotaForNewUser` 赠送保持不变。已有余额与历史推广总额都会保留;旧的注册奖励不会被追溯归属或回收。

## 策略与上线

在**计费 → 额度设置**中配置。`QuotaForInviter` 是固定奖励的原始额度单位(为 0 时关闭新发放)。`ReferralMinTopUpQuota` 是首次付费充值的最低入账平台额度,不是其货币金额。`ReferralMaxRewardQuota` 限制单次奖励上限(0 表示不额外封顶)。`ReferralPenaltyPercent` 默认 20,接受 0 到 100 的整数。`ReferralMaxPenaltyQuota` 限制额外罚扣上限(0 表示不额外封顶)。所有额度值必须是非负且 JavaScript 安全范围内的整数。支付合规确认仍然必需。已有奖励金额会被保留,本次迁移不会启用或提高它。`QuotaForInvitee` 是已废弃的兼容配置项,不再产生奖励效果。

首次通过校验的现金充值会写入永久资格标记,即使奖励处于关闭状态、未达到门槛、邀请方不符合条件,或账户历史上已有成功的现金充值。不要因为退款或申诉而重置该标记,也不会做追溯补发。手动完成订单被明确排除在推荐资格之外,也不消耗首次真实充值。由于历史手动完成订单无法与更早的付费订单可靠区分,历史成功现金记录会保守地消耗资格。

只有通过 `CompleteExternalTopUp` 完成的签名结算才发放奖励:Stripe、Creem、Waffo、Waffo Pancake 以及人民币 ePay 现金支付。LinuxDO 社区额度、钱包转账、赠送、管理员调整、手动完成以及订阅都不符合条件。标准的支付证据与额度容量校验继续生效。每个被邀请人只有一次奖励,每次充值只有一次奖励,并由数据库强制。支付入账、首充标记、奖励入账和流水记录在同一事务中提交或回滚。

## 治理与退款

普通的**禁用/启用**不会影响奖励。对确认的滥用或批量注册,请使用**因滥用封禁**,并要求提供证据,对应奖励会被撤销。额外罚扣勾选项默认关闭,并且需要管理员显式确认邀请方存在关联。仅凭同 IP 推断不构成受支持的自动罚扣依据。策略在奖励发放时被快照,之后的设置变更不会改变该次发放的罚扣规则。

`POST /api/user/manage` 接受 `action=ban_abuse`、`reason=abuse|bulk_registration`、`evidence`(1 到 1000 字节)、`penalize_inviter` 以及稳定的 `request_id`。重试时必须复用完全相同的载荷与请求 ID,改动会被拒绝。执行操作的管理员会按持久化的状态与角色重新校验,且必须高于目标账户。没有奖励就不会产生推广资金扣减。重复封禁不会对同一次发放再次扣减。

使用**撤销滥用封禁**(`action=restore_referral`、`reason=mistaken_ban`、证据、新的请求 ID、不带罚扣标记)可重新启用账户并追加冲正记录。在申诉之后重放已处理过的封禁,既不会再次禁用账户,也不会再次扣费。普通的重新启用不会静默恢复奖励。之后再次确认的封禁可以再次撤销已恢复的奖励,并产生新的修订记录。

对原始充值累计全额退款会撤销其推荐奖励,但不附加新的滥用罚扣。部分退款会保留奖励,直到原始支付金额被全额退回。如果全额退款发生在封禁之后,申诉可以撤销罚扣,但无法恢复已失效的奖励。退款供应方的校验与既有的付款钱包退款约束保持不变。

## 账务、隐私与运维

`users.aff_quota` 是带符号的奖励专用余额,负值表示欠账,后续奖励会先偿还欠账,之后才可能转出。购买所得的 `users.quota` 绝不会因推荐治理而减少,即使此前的奖励已经转出或消费。`aff_history` 仍然是历史累计获得额度,不是净收益。自助接口暴露非负的 `aff_quota` 以及 `aff_debt`。奖励历史接口 `GET /api/user/self/aff/rewards?before=<cursor>` 最多返回 50 条记录、可用余额、欠账和当前公开策略。身份只来自认证,不返回被邀请人邮箱、支付 ID 或私有证据。记录会分别展示发放、收回、罚扣和申诉冲正。

主迁移与快速迁移会创建 `referral_rewards`、`referral_ledger_entries`、`referral_moderation_events`,并添加首充与手动排除相关列。应用回滚时不要删除它们。所有结算与治理写入方必须一起回滚到该版本;旧二进制不理解首充契约,仍会发放注册奖励。启用策略之前请保留数据库备份,并运行随仓库提供的支付、并发、治理与退款测试。测试不会修改生产余额或配置。
