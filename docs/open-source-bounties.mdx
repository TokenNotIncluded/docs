## 1. 这是什么

开源赏金计划面向公开 GitHub 项目的真实缺陷。

项目赞助方可以用 API 余额托管修复奖励,支付一笔较低且平台公开的赏金费用,并邀请贡献者领取任务。贡献者可以提交可复现的 Issue、对应的修复 PR,或两者同时提交。

项目所有者批准提交后,被锁定的奖励会直接转入贡献者的 API 余额。

本指南与任何 Challenge II 恢复流程无关。平台不会预先配置、默认发布或自动置顶任何仓库,包括 `TokenNotIncluded/api.lmm.best`。所有项目都必须由赞助方使用自己的余额手动创建,所有者、管理员和普通用户适用相同的费用规则。

## 2. 核心原则

1. 只有真实、可复现的代码缺陷才符合条件。
2. 提交的 Issue 或 PR 必须属于赏金指定的 GitHub 仓库。
3. PR 必须围绕赏金目标,并包含相关测试或验证;如果同时提交 Issue,PR 必须引用该 Issue。
4. 发布赏金会立即扣除管理员配置且公开可见的赏金费用,并锁定全部奖励池。
5. 每日签到奖励计入通用余额,可以抵扣部分或全部赏金费用。
6. 项目关闭时只退还尚未使用的托管奖励,已收取的赏金费用不予退还。
7. 批准后奖励从托管直接转入贡献者余额,每个任务只支付一次。
8. 低质量报告、伪造缺陷、重复提交、无关 PR、纯机械清理改动以及仅为领取奖励而做的操作都不合格。

## 3. 赞助方如何发布赏金

### 3.1 创建草稿

在**个人资料 → 提交工单 → 开源赏金**中选择**创建赏金**,并提供:

- GitHub 仓库 URL
- 赏金标题
- 范围与目标缺陷描述
- 验收与验证规则
- 每个修复的奖励金额
- 奖励名额数量

创建与编辑草稿不扣费,也不会在赏金市场显示。

### 3.2 发布并托管奖励

发布时的总成本:

`每个修复的奖励 × 名额数量 + 赏金费用`

其中:

- 奖励池进入系统托管,只能用于已批准的转账,或在项目关闭时退还未使用的托管资金。
- 赏金费用由管理员设置并公开显示,按奖励池总额的一定百分比计算,当前默认为 `1%`。该费用快照随项目保存。费用由赞助方承担,不从贡献者奖励中扣除,项目关闭时也不退还。
- 每日签到奖励直接计入账户余额,可以用于支付全部或部分赏金费用。
- 赞助方余额不足时发布失败。
- 平台所有者或管理员发布自己的项目同样要使用自己的余额支付,没有特殊豁免。

### 3.3 管理进行中的赏金

发布后,赞助方可以:

- 暂停:暂时停止接受新的挑战者,已领取的任务继续保留。
- 恢复:重新开放剩余名额。
- 查看完整生命周期:参与者、Issue 与 PR 状态、完成说明、审核结果和余额流水。
- 取消未提交的任务:贡献者已领取但未提交时,赞助方可以取消并释放名额。
- 打赏:用自有余额即时打赏,肯定部分但有价值的工作。
- 关闭:结束赏金并退还尚未使用的托管奖励。

当仍有任务处于 `accepted` 或 `submitted` 状态时,赏金不能关闭。

赞助方只能取消没有提交的任务。已提交的任务必须先批准或拒绝;取消不能成为绕过审核的方式。

贡献者也可以主动退出。

被拒绝后有 7 天申诉窗口。在申诉期间且尚未建立争议时,相关奖励名额与托管资金保持冻结,赞助方不能立即关闭并退还这些资源。

一旦贡献者发起争议,冻结会持续到管理员裁决。只有在拒绝被否定,或 7 天期限届满且无人申诉时,冻结资金才会释放。

### 3.4 审核与转账

贡献者提交结果后,赞助方必须核实:

- Issue 描述的是真实且可复现的缺陷。
- Issue 包含受影响的项目或模块、复现步骤、预期行为、实际行为和影响。
- 同时提交 Issue 与 PR 时,PR 必须引用该 Issue。
- PR 只改动解决赏金目标所需的文件。
- 修复有效,并包含合理的测试或验证。
- Issue 或 PR 属于赏金仓库。

审核结果:

- 批准并转账:系统扣除一份奖励,直接计入贡献者余额。该操作幂等,不能重复执行。
- 拒绝:不支付奖励,并开始 7 天申诉期。申诉期间奖励与名额保持托管状态。

只有在第三方管理员否定申诉,或 7 天内无人申诉之后,托管资金才会释放、名额才会重新可用。

当所有奖励名额都被批准后,项目自动标记为完成。

赞助方必须给每位贡献者 `1-5` 的评分和公开反馈。评分、评论和贡献者平均分对双方以及争议管理员可见。

## 4. 贡献者如何参与

### 4.1 领取任务

在赏金市场中选择仍有名额的项目,点击**领取挑战**,然后填写你的 GitHub 用户名。

系统会为该贡献者预留一个奖励名额。同一用户不能重复领取同一个赏金。

赞助方不能领取自己发布的赏金。

### 4.2 查找并记录真实缺陷

提交 Issue 时,在赏金仓库中创建有效的 GitHub Issue,并至少包含:

- 受影响的项目或模块
- 复现步骤
- 预期行为
- 实际行为
- 缺陷影响

不要创建人为构造的 Issue、重复 Issue、无法复现的案例,也不要把仅求助的问题当作赏金 Issue 提交。

### 4.3 提交聚焦的修复

提交 PR 时,确保 PR:

- 同时提交 Issue 时引用对应 Issue
- 只改动修复该缺陷所需的文件
- 增加有意义的自动化测试、回归覆盖或可验证的验证步骤
- 属于赏金仓库

同一个 PR 不能重复用于领取奖励。

### 4.4 在系统中提交

进入**开源赏金 → 已领取挑战**并提交:

- GitHub Issue URL 或 GitHub PR URL(至少一个,两者都可选)
- 可选的完成说明

系统会校验仓库归属,并拒绝重复使用同一个 PR。

### 4.5 直接审核与结算

贡献者提交后,项目所有者直接审核 Issue、PR 和说明。

批准后,奖励计入贡献者的 API 余额,可用于平台支持的模型。

被拒绝时,贡献者可以在 7 天内提出争议。该窗口内奖励与名额保持托管。

申诉期满未处理或被否定后,任务结束,名额重新可用。

贡献者可以在审核完成前退出。退出后预留名额会被释放,已经投入的时间不予补偿。

审核完成后,贡献者可以对发布方或验证方给出 `1-5` 评分和公开评论。赞助方信誉显示在赏金市场,贡献者信誉显示在领取页面。单条评价、评论内容、平均分和次数对双方可见。

这套信誉机制对恶意拒绝、不公平低分和低质量交付形成社会约束。

## 5. 部分工作与打赏

打赏是赏金奖励之外的链下直接转账:

- 赞助方可以在任务进行中打赏,包括对有明显进展的部分完成工作打赏。
- 打赏从付款方余额扣除,直接计入贡献者。
- 打赏不减少托管奖励,也不代表正式验收。
- 打赏一经发出不可退还;UI 与 MCP 必须在提交前确认金额、接收方和后果。
- 管理员可以查看累计打赏记录,了解双方之间的历史资金往来。

## 6. 争议工单与第三方仲裁

当支付或验收出现争议时,任何一方都可以在任务卡片中选择**开源赏金争议**,填写任务 ID、原因、标题和事实摘要。

普通退款、技术或计费工单仍通过邮件处理;赏金争议会持久化在系统内,由第三方管理员审核。

被拒绝的贡献者必须在拒绝后 7 天内提交争议。系统在该期间保留托管奖励和名额,赞助方无法通过关闭或对账来消除申诉机会。

每个任务每方只能开启一个最终争议案件。案件解决后不能重新开启以再次冻结资金;只有在没有未决案件时,另一方才能提交自己的案件。

典型情形:

- 修复已合并且满足公开要求,但赞助方拒绝付款。
- 提交符合约定却被拒绝。
- 赞助方在发布后更改验收规则。
- 骚扰、滥用或其他不当行为。
- 其他需要中立评审的赏金分歧。

系统把争议关联到规范的后端记录,而不是信任 URL 查询参数。关联记录包括项目、仓库、Issue、PR、原始提交、验收说明、奖励、打赏、托管流水、评分和评论。

争议开启期间:

- 双方看到“等待第三方评审”状态和原始提交。
- 托管奖励与奖励名额保持冻结。
- 已有评分与信任历史可见。
- 管理员必须保留原始验收理由、争议陈述和最终结论;结论不能抹去原始证据。

管理员可以采取两种处置:

- 从托管中支付:确认 Issue、PR 与完成的有效性,并从赏金托管中向贡献者转出一份奖励,把任务标记为已批准。该操作只能执行一次。
- 驳回申诉:不进行正式奖励转账,记录中立的管理员结论。驳回表示当前证据不足或主张不成立,并不自动意味着申诉方恶意。

仲裁人必须是真正的第三方。如果管理员同时是同一任务的赏金所有者或受让人,系统会在同一数据库事务中阻止支付与驳回两种操作。

仲裁结果、状态和时间线对双方可见。支付与驳回操作在 Web 和 MCP 中都要求显式二次确认。

## 7. MCP 全流程支持

每个用户都可以生成专用的个人 MCP 令牌,并使用 Bearer Token 访问 `/mcp`。

MCP 遵循 MCP `2026-07-28`,使用无状态可流式 HTTP。数据库只保存令牌哈希,明文只在生成或轮换时出现一次,并可随时吊销。

Web 应用提供一键复制的提示词,其中包含端点、MCP 规范版本、认证方式和操作准则。

MCP 覆盖完整生命周期:草稿、发布、领取、提交证据、验收、支付、拒绝、打赏、评分、发起争议、查询争议以及管理员裁决。

对于涉及余额、托管、退款、退出、公开评分或争议裁决的敏感操作,AI 必须在显式确认前展示确切的动作、目标、证据、费用以及余额影响。确认状态与用户、工具和规范化参数绑定,有效期很短且只能使用一次。

发布、验收支付、拒绝、关闭退款、打赏、评分、争议创建与裁决、草稿删除和退出,都与业务变更在同一事务中持久化。如果响应丢失,重试会返回已提交结果,不会重复扣费、转账、评分或冻结。

## 8. 余额与退款规则

假设赞助方设置:

- 每个修复的奖励:`20`
- 名额:`3`
- 管理员赏金费用:`2.5%`

一次性发布扣费:

`20 × 3 + 60 × 2.5% = 61.5`

资金流向:

- `60` 进入奖励托管。
- `1.5` 为平台赏金费用,不予退还。
- `1.5` 可以用签到奖励或赞助方通用余额支付。
- 每个批准的修复从托管中转出 `20` 给贡献者。
- 如果在 1 个修复获批后关闭项目,剩余 `40` 退回赞助方余额。
- 已转出的奖励与平台赏金费用不予退还。

系统日志包含费用记录、托管转入转出、普通与争议转账、打赏转账以及托管退款。

## 9. 状态定义

### 项目状态

- 草稿:未付款且不可见。
- 已发布:在赏金市场可见并接受挑战者。
- 已暂停:不再接受新的挑战者。
- 已完成:所有奖励名额均已支付。
- 已关闭:手动关闭,未使用的托管资金已退回。

### 任务状态

- 已领取:贡献者预留了名额,尚未提交证据。
- 已提交:已提交 Issue 或 PR 以及完成说明,等待审核。
- 已批准:审核通过且奖励已转出。
- 已拒绝:审核未通过,奖励与名额继续托管 7 天。
- 已退出:贡献者退出挑战。
- 赞助方取消:赞助方取消了未提交的任务,名额被释放;已提交的任务不能进入该状态。

### 争议状态

- 待处理:证据与资金冻结,等待管理员核实。
- 支付解决:管理员确认并执行了托管转账。
- 已驳回:管理员未批准,并把结论与时间保存为可见记录。

## 10. 奖励不合格情形

示例包括但不限于:

- 无法复现或无影响的 Issue。
- 伪造、强行构造或夸大的缺陷。
- 已存在的重复 Issue。
- 与赏金无关或明显超出范围的 PR。
- 纯机械改动(格式化、依赖升级、批量查找替换)。
- 缺少测试或无法验证的修复。
- Issue 或 PR 不在赏金仓库中。
- 同一个 PR 重复提交。
- 垃圾信息、骚扰、自动化刷奖励。
- 动机只在于领取奖励而非解决真实工程问题的代码改动。

初次验收由赞助方负责。若产生争议,第三方管理员基于系统证据作出的裁决为最终结果。

## 11. 简短宣传文案

找到真实缺陷,记录可复现步骤,同时提交 Issue 与修复 PR。赞助方审核通过后,托管奖励直接转入你的 API 余额。

任何人都可以用自己的余额发布开源赏金,包括维护者。平台不会默认置顶任何项目:发布时全额奖励进入托管,并收取由管理员配置且公开可见的低额费用。每日签到奖励可以直接抵扣该费用。平台提供部分打赏、公开双向信誉和第三方争议工单。如果已合并的修复被无依据拒绝,管理员可以核实证据并强制从托管中转账。
